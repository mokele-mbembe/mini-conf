# 0012 MVP 上线运营闭环 / 平台管理模型 / 实施顺序澄清

## 背景

当前仓库已经完成了配置中心的核心业务主路径：

- 项目、配置文件、环境、部署实例
- Current Draft / Saved Versions / Release
- preview-bundle / publish
- deployment instance 激活、停用、归档、删除
- 项目级成员权限、审计日志、sync records、heartbeats 后端接口

但如果目标从“本地开发闭环”转向“可交付、可上线、可长期运营”，MVP 的剩余重点不应再只围绕前端页面补全，而应先补平台级骨架。

这份文档用于固定新的 MVP 主线顺序，并澄清哪些部分属于上线前必须完成的大块设计。

## Q1: 当前 MVP 主线要怎么重新排序？

新的主线顺序固定为：

1. **平台级权限模型 + 用户管理**
2. **系统初始化与上线实施方案**
3. **上线安全基线补齐**
4. **资源生命周期与文案收口**
5. **低风险页面和交互补齐**
6. **中间实施文档压缩整理**
7. **最后再做配置编辑体验统一升级**

结论：

- 后续不再把“继续补业务页面”默认视为第一优先级
- 先完成“平台能上线并长期运营”的骨架
- Draft / Diff / Merge 的统一编辑体验仍然重要，但顺序后移

## Q2: 交付给生产的系统，初始身份模型应该是什么？

MVP 交付时，系统应满足：

- 生产部署时内部数据全部由系统操作产生
- 系统只内置一个初始平台管理账户
- 该账户负责平台初始化和系统管理
- **该账户默认不具备项目业务数据可见性**

这意味着需要把当前“登录用户 + 项目成员”模型分成两层：

### 平台层角色

- `platform_admin`

职责：

- 初始化系统
- 创建和管理用户
- 创建项目壳
- 指定项目首个项目管理员
- 查看系统级配置和初始化状态
- 查看平台级审计

限制：

- 默认不自动成为任何项目成员
- 不因平台管理身份而直接看到项目业务数据

### 项目层角色

- `admin`
- `editor`
- `viewer`

职责延续当前项目成员模型。

结论：

- 平台管理权和项目业务访问权必须分层
- 后续 API、页面导航和审计边界都应按此模型调整

## Q3: 项目创建语义要如何调整？

当前澄清文档 `0005` 中曾固定：

- 任意已登录用户都可以创建项目

如果要满足“平台管理账户默认见不到业务数据”，MVP 应改为：

- 只有 `platform_admin` 可以创建项目
- 创建项目时必须指定至少一个项目 `admin`
- 创建项目后，`platform_admin` 默认不自动加入该项目
- 只有显式加入项目成员后，某个用户才可见该项目

这会影响：

- `GET /api/projects`
- `POST /api/projects`
- 项目创建 wizard
- 初始化脚本
- 平台级审计与项目级审计的边界

## Q4: 用户管理在 MVP 中要做到什么程度？

MVP 不做完整 IAM，但用户管理应一步到位采用可长期运营的模型。

建议范围：

### 必做对象模型

- `users.status = active | disabled`
- `must_change_password`
- `last_login_at`
- `password_updated_at`

### 必做管理能力

- 创建用户
- 禁用 / 启用用户
- 重置密码
- 强制下次登录修改密码
- 查看某个用户加入了哪些项目
- 为用户添加 / 移除项目成员关系

### 不进入 MVP

- 物理删除用户
- SSO / OAuth
- 细粒度权限点配置
- 组织树 / 多租户

原因：

- 用户是审计主体
- 物理删除用户会破坏审计与历史发布责任链
- 对当前 demo 和长期使用场景来说，`active / disabled` 已足够

## Q5: 系统初始化和上线实施方案要做到什么程度？

MVP 交付时必须附带完整的初始化和上线实施方案，而不再假设操作者依赖某个固定 Linux 发行版或手工修改 seed。

建议交付为两部分：

### 1. 初始化 CLI / init 脚本

负责：

- 初始化数据库
- 运行 migrations
- 创建首个 `platform_admin`
- 初始化系统级设置
- 可选导入首批用户

### 2. 首次登录 Setup Wizard

首个 `platform_admin` 登录后完成：

- 修改初始密码
- 创建首批用户
- 创建第一个项目
- 指定项目管理员
- 创建第一个环境
- 创建第一个配置文件 / 模板实例

### 部署交付要求

MVP 至少应给出两种可执行部署方案：

1. `Docker Compose`
2. 通用 Linux 二进制 + PostgreSQL + 反向代理 runbook

结论：

- 初始化能力属于 MVP 主线，而不是文档附赠项
- 后续实现不应再把 seed 文件视为唯一用户与项目初始化手段

## Q6: 上线安全基线在 MVP 中应做到什么程度？

结论是：**尽可能完善，并视为 MVP 必做。**

建议纳入 MVP 的安全基线：

### 管理端

- Session Cookie：`HttpOnly`、`Secure`、`SameSite`
- CSRF 防护
- 基础安全响应头
- 登录失败节流
- 首次密码修改和密码强度规则
- 高风险操作确认

### 开放消费端

- Bearer Token 校验
- 基础限流
- 关键失败事件记录
- 请求链路日志

### 审计

- 平台级审计
  - 用户创建 / 禁用
  - 项目创建
  - 初始化动作
- 项目级审计
  - 配置编辑
  - 发布
  - token 重置
  - 实例生命周期操作

### 敏感数据

- 管理端读取、diff、日志、审计保持统一脱敏
- 不输出明文 secret / token / draft content

## Q7: 资源生命周期统一这件事，MVP 要做到什么程度？

当前结论不是“所有资源都强制同构”，而是：

- 不要求所有资源拥有完全相同的生命周期机制
- 但要收口成一套一致的文案和删除原则

建议：

### Projects

- 保持 `active | archived`
- 对“错误创建、从未投入使用”的项目提供删除能力
- 删除前必须检查未被业务数据引用

### ConfigFiles

- 保持 `active | archived`
- 对“错误创建、从未投入使用”的配置文件提供删除能力
- 删除前必须检查没有 draft / release / sync / heartbeat 依赖

### ProjectEnvironments

- 保持 `active | inactive`
- 未被实例引用时可删除

### DeploymentInstances

- 继续保持当前特殊模型：
  - `active | inactive`
  - `is_archived`
  - `deleted_at`
  - `deployment_uid`

原因：

- deployment instance 涉及 token、sync records、heartbeats、deployment key 释放和历史审计
- 它天然比项目、配置文件、环境更复杂

### Users

- 一步到位采用完整管理模型
- `active | disabled`
- 不做物理删除

### 文案统一

后续页面和错误码需要统一这些词：

- `active`
- `inactive`
- `archived`
- `disabled`
- `delete`
- `restore`

## Q8: 低风险功能和文档整理要怎么安排？

顺序固定为：

1. 先完成平台骨架和安全基线
2. 再补低风险页面与交互
3. 再压缩中间实施文档
4. 最后统一升级配置编辑体验

### 低风险功能补齐的范围

- 创建项目入口
- 项目成员页
- sync records 页面
- heartbeats 页面
- audit logs 页面
- 非 admin/editor/viewer 的真实联调与 E2E

### 文档压缩目标

后续建议把文档收成三层：

- `constraints/`：最终规则真值
- `runbooks/`：部署、初始化、运维、恢复
- `archive/`：阶段性协作与 handoff 文档

## Q9: 配置编辑体验统一升级为什么放到最后？

不是因为它不重要，而是因为：

- 先上线并长期可运营，比先打磨编辑器体验更关键
- 当前系统已经具备基础 Draft / Release / Diff 能力
- 在平台权限、初始化、安全和资源模型未收稳之前，过早切入大规模编辑器升级会分散主线

因此当前顺序固定为：

- 先做平台骨架
- 再做低风险补齐
- 最后推进 `Config Workspace`

## 当前结论

- MVP 剩余的大工程优先级已经调整
- 当前最值得推进的不是单纯页面补齐，而是：
  1. 平台级权限与用户管理
  2. 系统初始化与上线实施
  3. 上线安全基线
  4. 资源生命周期与文案收口
- 配置编辑体验统一升级仍然保留，但顺序后移到上述骨架完成之后
